# CI-17 · CI nativo con servicio postgres:16

**Origen.** Decisión de arquitectura en Google Cloud: tanto los PR como los push a `main` en GitHub Actions ejecutan de forma uniforme contra el servicio `postgres:16` efímero dentro del runner.

**Costo.** 0 USD: el servicio `postgres:16` corre dentro del runner de GitHub Actions, en los minutos del plan. La alternativa descartada, un Cloud SQL de pruebas `db-f1-micro` siempre encendido, costaba unos 9-10 USD/mes.

## Entrega
- En `zero-regression-pipeline.yml`, todos los flujos (PR y push a `main`) usan el servicio `postgres:16`: base vacía, migrada con `alembic upgrade head` dentro del job y sembrada de forma reproducible, manteniendo los mismos nombres de trabajos y checks obligatorios de `main`.
- El arnés del push a `main` puede paralelizarse como el de los PR (plantilla clonada), porque ya no comparte una base remota.
- Se actualiza la metodología 14 en `governance/METODOLOGIAS.md` y se alinea `governance/operaciones/PRUEBAS_DE_HUMO.md` al servicio `postgres:16` en contenedor.

## No hagas
- No tocar la lista de checks obligatorios de `main` ni los nombres de los trabajos.
- La conexión de pruebas del CI apunta exclusivamente al servicio `postgres:16` interno del job.

## Quién la aplica
Una persona, porque toca `.github/workflows/`, que es gobernanza reservada. La sesión de IA puede preparar el diff y la prueba, pero no lo empuja a `main`.

## Hecho cuando
Toda ejecución hacia `main` pasa contra el servicio `postgres:16` con los checks obligatorios en verde.
